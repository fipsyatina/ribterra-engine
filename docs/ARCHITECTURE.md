# Ribterra architecture

Version 0.10 adds per-resident Move/Gather admission, persistent manual queues, explicit gathering completion and player control leases. It uses **protocol 7/rules 7/generator 2/save 8**. The full engine remains unfinished; current validation and the verified package are tracked separately in [VALIDATION.md](VALIDATION.md). Contracts: [manual orders](MANUAL_ORDERS.md), [professions](PROFESSIONS_PLAN_UA.md), [skills](SKILLS.md), [save format](SAVE_FORMAT.md). All 38 original requirements and V01–V03 in [ENGINE_REQUIREMENTS.md](ENGINE_REQUIREMENTS.md) remain in scope.

Historical version 0.8 added persisted gathering continuations and construction worker replacement to physical inventory and delivery, using save 6 and protocol 5/rules 5/generator 2. Its local 40/40 CTest, five-locale GPU, benchmark and package checks passed; CI source `f62cea0` passed Windows 40/40, Linux 26/26 and UBSan 8/8. Previous 0.7 local Windows 37/37 and CI Windows 37/37, Linux 24/24 and UBSan 7/7 apply only to that version. [WORK_INTENTS.md](WORK_INTENTS.md) preserves the 0.8 module contract. The bounded two-layer world, FIFO planner and typed two-phase path replies remain the foundation.

## Executable and target boundaries

The current dependency direction is:

```text
Ribterra ──> GameUI ──> AssetPipeline / Localization
        ├──> Presentation ──> NetworkSession ──> Protocol ──> GameServer ──> SimCore ──> Foundation
        └──> Renderer2D
                                              └─> NetTransport
RibterraServer ────────────────────────────────> NetworkSession
RibterraNetProbe ──────────────────────────────> NetworkSession
SimRunner ─────────────────────────────────────────────────────> SimCore
```

- `Foundation` owns hashes, secure random tokens, UTF-8 validation, atomic file replacement, and narrow platform adapters.
- `SimCore` owns the deterministic fixed-step world and complete authoritative `WorldState`. EnTT 3.16 stores authoritative identity, position, activity, vitals, skills, routes and path-order state; stable-ID collections hold physical stacks, storages, item reservations, logistics tasks, construction orders and work intents. ID-sorted DTO views keep serialization and presentation order stable. A bounded FIFO planner advances one shared reverse BFS per batch across ticks, including internal pickup/dropoff and work routes. A separate bounded scheduler admits gathering continuations and replacement builders to that planner. Its public headers do not expose SDL, GPU, audio, Steam, RmlUi, or GameNetworkingSockets types.
- `GameServer` is the only gameplay writer. It authenticates a player identity, orders commands at tick boundaries, validates requests, deduplicates request IDs, correlates path batches with requests, filters snapshots, and owns chat/session state.
- `NetTransport` is a private-pimpl standalone GameNetworkingSockets adapter. It owns direct IP listening, connection lifetime, bounded messages, and command/chat/snapshot lanes.
- `Protocol` serializes verified FlatBuffers frames, applies zstd bounds, and converts only player-visible state to full or baseline-relative chunk deltas. Large snapshots are split into bounded parts and assembled transactionally before client state changes. Command replies carry `Queued`, `Applied`, or `Rejected` plus a typed path-failure reason.
- `NetworkSession` performs the challenge/join flow, version and content checks, phase-specific reply acknowledgements, resynchronization, chat delivery, autosave, and the dedicated-server loop boundary.
- `Presentation` reads a const `ClientSession`, maps input to typed commands, and composes a backend-neutral `Frame2D`. Its ordered geometry/text command stream keeps terrain, shared isometric world depth, fog, panels, and overlays in painter order. It cannot mutate `World` directly.
- `Renderer2D` owns SDL_GPU resources, text rasterization and an explicit software test adapter. It receives only `Frame2D`, never `World`, `GameServer`, `ClientSession`, or gameplay commands. Windows production startup requests `direct3d12`; software rendering requires `--software` and is never an implicit fallback.
- `GameUI` owns the single RmlUi context, converts Rml geometry into ordered `Frame2D` UI commands, and emits intent for the application to route. It does not gain simulation authority. Surface/Mine tabs and Page Up/Page Down change only the viewed layer. Use passage becomes a normal server-validated move for the selected resident. Text input focus consumes gameplay shortcuts; chat and names are inserted as escaped text. Menu, settings and Help can exist before a `ClientSession`, while Continue and Help Back preserve an existing local or remote session.
- `AssetPipeline` exposes only manifest-registered, confined relative paths and verifies packaged bytes. `Localization` loads the five flat locale catalogs and formats named ICU arguments and plurals. See [ASSETS.md](ASSETS.md) for staging, hashes, licenses, font coverage, native UI validation and offline atlas metadata.

`Ribterra` creates an embedded `GameServer` for local play. Local and remote input therefore pass through the same command validation and visibility-filtered `ViewSnapshot`. `RibterraServer` runs the same GameServer without a window, GPU, or Steam client.

## Authority and network state

Every network command carries a request ID and issued tick, but the transport connection supplies the authenticated player ID. The server rejects unauthenticated sessions, observer commands, altered request reuse, invalid coordinates, hidden gathering targets, oversized resident lists, rate-limit excesses, and version/content mismatches. Repeating the same accepted request returns its cached result instead of applying the effect twice.

Joining uses a random server challenge. When a server password is configured, the client sends an HMAC-SHA256 proof bound to the nonce, player name, resume token, and protocol/rules/content versions. The password itself is not placed in the Ribterra packet. GameNetworkingSockets provides the encrypted direct IP connection and reliable delivery used by the current session layer.

The server emits only `ViewSnapshot`, never `WorldState`. The current projection retains the 0.8 chunk visibility rules: unexplored cells are replaced with the canonical empty hidden value, hidden buildings are omitted, and only residents of the currently controlled nation are sent. Visible residents include their order phase, typed path failure, and pending batch identity. The logistics projection adds controlled-nation inventory totals/available/reserved quantities, resident cargo/task status, and construction delivery/work summaries. `ResidentWorkView` adds kind, phase, failure, completion and attempt count for an owned resident, without duplicating inventory or exposing intent targets and IDs. Visible owned sites add worker phase, failure and assigned count, derived from current routes and physical presence rather than a stale resident target. These collections support keyed delta and removal with owner-reference checks after atomic merge. The snapshot does not serialize authoritative reservation tables or hidden source coordinates. A newly discovered portal reveals only its paired exit cell; it does not reveal surrounding ore or caves. Internal chunk revisions never cross the wire.

Full snapshots establish a world-ID/revision baseline. Later messages carry changed chunk cells, entities, counters and removals. A snapshot may contain at most 128 parts. `SnapshotAssembler` accepts parts in any order, rejects conflicting duplicates and inconsistent metadata, caps buffered state at 16 MiB, expires incomplete assemblies after 10 seconds, and applies the joined snapshot once. Frames still enforce compressed, expanded, semantic, and collection limits. The 0.5 integration coverage exercises a 19-part transfer of all 128 chunks, late join, mine movement, foreign-unit denial, reconnect, timeout/resync, premature acknowledgement rejection and save continuation.

All current players share control of cooperative nation 1. Assign/Stop reject foreign residents individually while retaining valid outcomes for owned residents; legacy Move/Gather batches remain atomic. The current 6000-resident validation ceiling is a provisional safety bound for four-nation fixtures, not a supported product population or a replacement for the required 4×1500 benchmark. The server chat has Unicode validation, a five-message-per-ten-second limit, a 200-message in-memory history, and per-recipient mute support. The graphical HUD exposes local and remote chat, while lobby roles, persistent moderation, LAN discovery, and Steam transport remain pending.

Path commands have two reply phases. `Queued` confirms admission only; `Applied` is emitted after search, reconstruction and staging commit, while `Rejected` carries a typed failure without partial batch application. Internal `Logistics` and `Work` paths are consumed by their simulation owners and do not emit client command replies; the server also excludes them from external request correlation. Phase-specific receipts allow a terminal acknowledgement to clear both terminal and earlier `Queued` state. A late lower phase is acknowledged without replacing the terminal result, and altered reuse of a request ID closes the connection. Ordinary disconnect does not cancel queued work; the terminal reply remains available during the in-memory reconnect window. A process restart loads the simulation world but starts new sessions, so durable credentials and uncertain-command deduplication across restart remain open.

## World representation

The current world retains the bounded grid introduced before 0.7 and spans coordinates `[-96, 160)` on each axis. It pre-creates an 8×8 grid of 32×32 chunks for each of two layers: 64 surface chunks and 64 mine chunks. This fixed set of 128 chunks establishes the data boundary but is not streaming or chunk eviction. Negative-coordinate conversion uses floor division, so cells next to zero map to stable chunk keys and local indices. Terrain hash arithmetic converts operands to `uint32_t` before multiplication; this avoids signed-overflow undefined behavior at boundary chunks.

The surface and mine connect through an explicit portal whose current endpoints are both `(28, 24)` on their respective layers. Cross-layer routes must use that portal. `MineOre` is solid; gathering an adjacent ore cell reduces its amount and turns a depleted cell into walkable `MineFloor`. Terrain, residents and buildings all carry a layer. Routes store explicit layer-qualified points and optional work targets, including valid negative coordinates.

## Budgeted path planning

Path requests enter a deterministic FIFO of bounded batches. A batch with one destination performs one shared reverse BFS: from the destination for movement and from its passable neighbours for work. Each tick spends at most 4096 work units across search expansion, route reconstruction and staging. Neighbours use the fixed `N, W, E, S, portal` order, and resident IDs are canonicalized. Legacy and Build batches retain atomic application. New manual batches resolve residents independently, so an unreachable member does not discard reachable members' accepted queues. Move/Gather command receipts acknowledge queue admission with stable order IDs; physical completion appears in the manual-order projection.

The planner bounds queue length, route length, staged cells and memory. It records a 1200-tick deadline and at most three topology restarts. Save format 8 retains the FIFO, active phase, frontier, parent nodes, reconstruction cursors, staged routes, reservations, work counter, next batch ID, topology revision and pending outcomes, plus manual-order correlation and per-resident resolution. Historical batches retain their frozen logical accounting costs during migration. Hierarchical routing, flow fields, reusable route caches, local crowd avoidance and collision handling remain separate required work.

## Physical inventory and construction

An item stack owns one quantity at one ground, storage, carried or construction location. Reservations belong to tasks and cannot exceed their source quantity. A resident carries at most ten units of one item kind. Pickup transfers the reserved quantity into a carried stack; dropoff transfers that same cargo into storage or the construction site. Internal path replies advance task legs without creating synthetic client command replies. Gathering produces physical output, food consumption uses available stored food, and construction work starts only after every required material has arrived.

Build admission atomically reserves the full cost. Its external `Applied` reply still marks path commit and creation of the delivery-stage building; completed construction is a later simulation event. Cancellation releases outstanding reservations and returns materials physically. Work-stage cancellation preflights refund capacity before changing state. Task failures, carrier death and full/incompatible destinations retain cargo as physical items. Save state carries every task phase and correlation; the top HUD shows available inventory, while the inventory panel exposes totals, reservations, cargo and construction progress.

Collections are bounded to 65,536 stacks, 8,192 reservations and 4,096 logistics tasks. The scheduler limits transitions separately from the path planner. These limits do not establish the full tick or memory performance gate. Roads, danger costs, production recipes, upgrades, caravans, food spoilage, richer ownership and the full material catalog remain required work.

## Persisted work admission

A successful physical dropoff stays `Complete`. `GatherContinuation` owns subsequent admission to a work route; `BuildAssignment` reserves one idle resident of the site's nation when a paid Work site has no valid worker. The scheduler retains at most 8192 intents, visits at most 128 records/sites and makes at most 32 admission attempts per tick. Retry delays are 2, 4, 8, 16 and then 32 ticks, with at most 64 attempts and a 1200-tick admission deadline. Saved scheduler cursors preserve the traversal order across load. These bounds do not establish a CPU-time or full population-performance result.

`Waiting` and `PathPending` carry no failure or completion; `Complete` has a normal completion reason, and `Failed` has a typed path failure. `Started` means that the planner handed the route to the resident, not that the resident arrived. Exhaustion of the expected resource is a normal `Exhausted` terminal. Work progress requires arrival at an adjacent site cell; replacement does not charge materials again. A Work site without a candidate is shown as `Waiting`, with zero assigned workers and no synthetic resident-zero intent.

Rejected manual admission leaves the old intent and pending Work route intact. Accepted Move/Gather supersedes the old work history and cancels only its correlated internal Work batch before installing the new command. If that newly admitted route later fails, the previous intent is not restored. Reserved cargo keeps its independent logistics rules. New manual work or automatic hauling retires old Exhausted/Failed display history. See [WORK_INTENTS.md](WORK_INTENTS.md) for cancellation, topology retry, failure retention, migration and acceptance scenarios.

## Professions and skills

`ProfessionState` retains the requested assignment, worksite, priorities and manual/deferred state independently of `Job`. The selector uses bounded visits/admissions and sends work through existing path, work-intent and physical-logistics owners. Assign/Stop return Applied/Deferred/Rejected for each requested resident; accepted changes during protected delivery take effect at its physical boundary. Manual Move/Gather now use separate per-resident queues; Farmer, Smith, Medic and Guard still have valid state without executable work scenarios.

Each resident has eight permanent XP tracks, practice state and abilities. One data-driven server calculation caps the combined skill/ability/practice effect at ±15%. Owner-only `ResidentProfessionView` carries eight ready-to-display breakdowns through full/delta/removal and multipart snapshots, while internal practice timestamps/debt, selector cursors and hidden worksites remain server-side. See [SKILLS.md](SKILLS.md) for formulas and [PROFESSIONS_PLAN_UA.md](PROFESSIONS_PLAN_UA.md) for the remaining AI scope.

## Manual orders and control

Each resident can have eight live manual orders; the world bounds all live and terminal records to 8192 and retains up to 256 recent terminal records. Replace preflights its target and capacity before removing the old queue. Append preserves existing work. OneDelivery gathering completes after physical dropoff; UntilExhausted keeps the continuation until normal exhaustion or a typed failure. Cancellation, Stop and Release retain protected cargo until its delivery boundary. Single-order cancellation records `Cancelled`; releasing authority records `Released`. The scheduler visits at most 1500 eligible heads and admits at most 32 shared path batches per tick; these counters do not bound all simulation work.

GameServer owns transient per-resident leases independently of saved order provenance. Selection does not claim a resident; the first accepted controlling command does. Only the holder can cancel, release or transfer, and transfer requires a connected eligible player. Disconnect keeps the lease for 30 seconds of monotonic time; expiry enters the same FIFO command boundary even while simulation ticks are paused. Loading a world starts a new control epoch and clears leases while preserving queues. Client actions retain their epoch so an old dialog cannot mutate a replacement world.

Snapshots expose owned queues, holder names, grace state and eligible transfer recipients, but not internal executor references, planner identities or provenance. Full/delta/removal and multipart assembly preserve these collections atomically. Paused command boundaries advance snapshot revision without advancing simulation ticks; transport retains changed revisions until acknowledged and skips unchanged projections. The ordinary running snapshot cadence remains 5 Hz. See [MANUAL_ORDERS.md](MANUAL_ORDERS.md) for limits and detailed semantics.

## Persistence format 8

The save container retains the `RIBSV2` magic and 96-byte header while declaring payload format 8, rules 7 and generator 2. It records the content hash, world ID, lengths, flags and checksum. Its zstd payload contains a FlatBuffers `WorldSave` with chunks and revisions, portals, layer-qualified residents and buildings, routes and planner state, item stacks, storages, reservations, logistics tasks, construction orders, work intents and scheduler cursors, derived resources, events, counters, tutorial flags, RNG seed, tick and stable IDs. Format 7 added professions and eight XP/practice/ability tracks; format 8 adds manual orders, optional issuance provenance, executor correlation and the manual scheduler cursor. Genuine format-7 migration validates the old world before wrapping active work, preserves atomic legacy batches and leaves the exact original as `.v7.bak`. Control leases are intentionally session state and are not loaded as authority.

Loading verifies container bounds and metadata, checksum, zstd size, FlatBuffers structure, enum/range/identity invariants, chunk order and uniqueness, routes and portals before replacing the live world. Saving writes and re-reads a temporary file, compares the round trip, retains the previous valid primary as `.bak`, then performs an atomic replacement. A missing primary may recover from `.bak`; a present but corrupted primary is reported instead of silently rolling back.

The frozen format-6 migration preserves legacy XP and planner/work/logistics state with `.v6.bak`. The frozen 0.7 format-5 contract migrates pending gathering continuation from a completed logistics task into a Work intent while retaining the same batch ID and search state; physical cargo and paid Work sites remain intact. Its original remains as `.v5.bak`, and genuine carry, continuation and Work fixtures accompany the baseline. The frozen 0.6 format-4 contract migrates global resources into Camp stacks, pending Build costs into physical reservations, and already-paid unfinished buildings into Work orders without charging twice, retaining `.v4.bak`. Format 3 initializes an empty planner queue and retains `.v3.bak`. The version 0.4 format-2 contract overlays its 48×48 surface cells at coordinates 0…47 and retains `.v2.bak`; text format 1 retains `.legacy.bak`. Supported older formats pass the applicable work, profession and manual-order migrations before being rewritten as format 8. Baseline schemas and `flatc --conform` guard compatible evolution. See [SAVE_FORMAT.md](SAVE_FORMAT.md) for the byte-level contract and current validation limits.

## Reproducible dependencies

The vcpkg manifest pins baseline `04a9d8e5212d01ee1dd9478eadd9caade4f8b0d4` and uses a static release triplet. A narrow GameNetworkingSockets overlay corrects its static protobuf linkage for this configuration. The desktop `renderer` feature installs SDL_shadercross 3.0.0-preview2 as a host tool with DXC 2026-05-27 and SPIRV-Cross 1.4.357.0. CMake compiles HLSL to DXIL plus JSON reflection and a manifest; only these results enter the runtime package. SDL SDK archives remain separately pinned by version and SHA256. `build/engine-windows` is the Windows preset output; the headless preset excludes SDL presentation and renderer tooling while retaining the server/protocol stack.

Schema-conformance tests cover the save, network payload, and network frame schemas. A source-boundary test recursively rejects platform, presentation, transport, and server dependencies from SimCore headers and implementation files.

The headless configuration exposes optional `RIBTERRA_ENABLE_UBSAN` support and a `headless-ubsan` preset. Historically, 0.5 Linux CI passed its four then-configured suites without runtime errors or compiler warnings; subsequent module suites and their version-specific results are recorded in [VALIDATION.md](VALIDATION.md). The 0.9 `42036ff` CI passed without C++ warnings or UBSan errors; the earlier `d3bc785` warnings are retained in VALIDATION; ASan and the broader long-soak gate remain open.

The build validates equal locale keys and ICU arguments, required font glyphs, asset hashes and metadata, and RML/RCSS before replacing the staged asset set. Validation or a rename exception preserves the previous directory; process termination between the two renames is not covered. `UiCheck` constructs and renders the real menu/HUD through the software backend; unsupported advanced RmlUi clip/layer/filter/shader features fail rather than silently disappearing. `AtlasTool` produces deterministic offline PNG pages and metadata, but current world geometry does not consume that atlas.

SimCore now links and uses EnTT 3.16. Catch2 3.16 remains installed and packaged but is not used by current test targets. EnTT integration alone does not satisfy the plan's complete AI, logistics, tooling, sanitizer, or performance requirements.

## Temporary and pending architecture

The renderer uses an offscreen RGBA target for deterministic captures, then presents the letterboxed result. SDL_GPU/D3D12, offline shader compilation, the Frame2D boundary, RmlUi geometry/textures and five-language UI have run on a physical NVIDIA GeForce RTX 3050 Laptop GPU. Version 0.5 also passes the native mine/save-resume visual probe, the server with two probes and a graphical GPU client, and the extracted-package network smoke. Twenty-three menu, settings, help, HUD, compact, mine and network PNGs were reviewed. RmlUi uses FreeType with staged Noto Sans; its generated glyph textures follow premultiplied-alpha semantics. SDL_Renderer exists only as the explicit software test backend.

Render budgets, streaming chunks, full biome/geology/cave generation, world atlas rendering, a complete texture registry, runtime asset/UI hot reload, invalid-shader fallback, miniaudio, the remaining logistics and production systems, path hierarchy/flow fields/cache/crowd avoidance/collisions, complete AI/combat/society systems, key rebinding, lobby and remaining colony screens, LAN discovery, durable sessions, Steam adapter, Metal/macOS and release content remain open.

The bounded 0.7 chunk world and provisional 6000-resident validation limit must not be used as evidence for the plan's final 4×1500 simulation, p95/p99 tick budget, 60 FPS target, memory budgets, cross-platform session, or Steam release gate. The planner and logistics scheduler bound their work, but full AI, crowd collisions, hierarchical routing, four simultaneous clients and the complete measured performance gate remain open.
