## Uncertainties that cannot be hidden

**v7 after updating the old save.** `migrate_legacy_professions` always does `resident.profession={}` for previous formats, keeping their routes/path/tasks/Work. After the usual save it is a real v7 with `manual_override=false` and an active external Move/Gather or cargo. So the lack of a flag is not proof of new professional automation or completion of work. Recommendation: the neutral compatibility executor keeps the previous execution without synthesizing the manual authority/new command. An unreasonably added manual override will change the eligibility of the old behavior.

**Deferred does not retain the name of the last command.** `automation_enabled=false` may be the result of a Stop or an explicit Assign with the automation turned off. The policy already recorded and the time of its application are renewed; You can't replace the original command name or CommandReply. After death or failure may remain pending leg for cleaning; It's no reason to let an actor back in the game.

**Report and terminal history is not a log of origin.** `retire_manual_override` does not always change `wait_reason` immediately; the indicator ManualOrder may be temporarily retained after completion. Work and logistics have a limited history. `complete_task` clears `resume_job` after creating a continuation; You should look for it through the active Work/Rout, not the last Complete task. `PathBatchOutcome` does not contain resident IDs or author/request; WorldState does not have a server request cache. The original authorship, group ID and release time of the already established route cannot be restored.

**Failed output does not always complete Gather.** If `gather_yield` does not find a cache, it creates a Ground output and Failed/StorageFull task, but leaves gather activity/route and returns XP as the actual output. The last failed task itself doesn't make the manual Gather terminal. And on the contrary, the failed task with pending logistics path is the old cleanup, not the delivery of cargo.

**The number of import-valid states is wider than the usual commands 0.9.** The Professional Validator allows `manual_override=true` for any active Work or physical task, without limiting it to GatherContinuation/ToDropoff. It can take, for example, a manual BuildAssignment or a pickup without gathering resume metadata. This is not proof that such action is caused by ordinary commands. Don't take fictional Gather from ItemKind or Build from Job himself. Such states require an agreed compatibility binding or a clearly limited support policy; You can't just take them off quietly.

## Minimum solutions before freezing DTO

1. **Compatibility binding.** It is recommended to keep the old executor separate from the new user row: `legacy continuation`, `cancel-at-boundary` and confirmed `manual head` have different values. Compatibility status should not create a second task/path/ reserve and a new control lease. For import-valid non-typical manual performers, an answer is required: opaque legacy binding or explicitly documented refusal. The advantage is to preserve their old semantics.
2. **Atomic legacy batch.** Converting an already started batch to a new partial early execution will change the tick arrival and results of the old save. It is recommended to leave imported v7 batches the old atomic commit mode with its budget charges, and give new commands per-resident execution. Otherwise, a clear decision on whether to allow a change in behavior is needed, not a statement of unchanged extension.
3. **Unknown origin.** New order IDs can be assigned deterministically from the resident ID; do not call them original IDs. Mark missing issuer/request/issued_tick values as unknown/legacy instead of inventing them from the current tick. Keep external `path_results` as old results without a new player receipt; `GameServer::load` begins a new epoch.
4. **One source of manual priority.** The new queue/compatibility state controls manual override; The stored field 0.9 should not be a second independent truth. The correlations child executor → manual head are mutually verifiable, but the row does not possess objects a second time.
5. **Check before conversion.** First full of the old semantic validation v7, then classification and wrapper adding metadata, then new transactional validation. Do not repair the old route cells/frontier/deadlines during import. Changes to fields that maintain semantics and rules for rejecting ambiguous states should be separate root solutions.
