# Міграція v7 до запропонованої ручної черги

**Статус: технічна пропозиція, не реалізована міграція.** Перевірено вихідний код 0.9 / `d3bc785`; переглянуті runtime/save файли не відрізнялися від цього коміту. Збірки, тести й пробні запуски в межах огляду не виконувалися. Справжні v7 fixtures окремо створює capture-процес із замороженої `.deps/v7-capture-d3bc785`; цей документ не підтверджує їхню готовність.

Висновок: для нових ручних дій 0.9 є достатній структурний доказ, але **одного `manual_override` для всього простору допустимих v7 недостатньо**. `Job`, `wait_reason`, останній terminal Work або останній logistics task також не визначають походження наказу. Потрібно розрізнити активний ручний наказ, завершення вже скасованого виконавця та нейтральне legacy-продовження. Загальний обсяг наступного етапу — у [CONTROL_PLAN_UA.md](CONTROL_PLAN_UA.md).

## Канонічні ознаки за фазою

| Стан v7 | Доказ і пріоритет джерела | Запропоноване відображення |
|---|---|---|
| Pending зовнішній Move/Gather | `Resident.order_phase == PathPending`, `pending_path_batch == B.id`, ID входить до `B.resident_ids`; відповідний draft має той самий actor/start. `B.command` явно Move/Gather, а `target`, `assigned_job`, `to_adjacent` перевіряються імпортом. `manual_override=true`, `deferred=false` підтверджують чинне ручне перевизначення 0.9. | Один ручний head на кожного відповідного актора з посиланням на **той самий** batch/draft. Ціль брати з batch: старі `Job`, `Route.work` і target мешканця можуть ще належати попередній роботі. Не перезапускати Queued/Search/Reconstruct/Stage. |
| Move після встановлення маршруту | `manual_override=true`, без новішого pending path/активного logistics/Work, `Job::Move`, `Route.work` містить призначену ціль; маршрут і позиція проходять загальну перевірку. | Running/Travelling Move зі старими points/cursor/позицією. Навіть `cursor == points.size()` не означає, що terminal callback уже відбувся: `tick` завершить Move на наступному проході. Не завершувати його під час import. |
| Gather у дорозі або за роботою | Ті самі виключення; `manual_override=true`, `Job` Woodcut/Mine/Forage, ціль у `Route.work`, поточний progress збережений. `cursor < points.size()` означає рух; вичерпаний маршрут може означати вже роботу або очікування першого work tick. | Чинний Gather у режимі **до вичерпання**, з поточним progress. Не перетворювати старий безперервний Gather на запропонований новий OneDelivery. Не скидати progress/XP і не додавати кредит. |
| Gather із вантажем | Чинний `HaulToStorage` / `ToDropoff`, той самий resident, `carry_stack_id` посилається на один Carried stack цього актора; `resume_job` є gather job, а `resume_target` — ресурс. `manual_override=true` підтверджує ручне походження. | Delivering Gather посилається на чинний task/stack; ціль збору брати з **resume_target**, не з маршруту доставки до Camp/Stockpile. За наявності `task.path_batch_id` залишити Logistics batch та його frontier. |
| Gather continuation / повторний допуск | `manual_override=true`; є рівно один активний `WorkIntentKind::GatherContinuation`. Waiting має Idle actor, без path, зі збереженими attempts/next_attempt/deadline; PathPending взаємно пов'язаний з одноакторним `PathCommandKind::Work`. | Ручний Gather очікує вже наявний Work executor. Не створювати другого intent, не скидати backoff/deadline й не робити нового пошуку. |
| Work `Complete/Started` | `finish_work(...Started, ..., false)` означає, що маршрут встановлений. Terminal history може бути очищена; вона не є обов'язковою умовою продовження. |
| Deferred Assign/Stop | `change_profession` уже записала нову assignment/automation_enabled, скинула `manual_override=false` і встановила `deferred=true`. Порядок розбору важливий: спочатку deferred/cancellation boundary, потім чинний фізичний task або Work, потім прямий pending batch, і лише без них — routed activity. У випадку Logistics `PathPending` належить перевезенню, а не новому Move до сховища. Move Replan (`B.command=Replan`, assigned_job Move, `manual_override=true`) зберігає попередній ручний Move; це також не новий наказ.

## Неоднозначності, які не можна приховувати

**v7 після оновлення старого save.** `migrate_legacy_professions` завжди робить `resident.profession={}` для попередніх форматів, зберігаючи їхні routes/path/tasks/Work. Після звичайного save це справжній v7 із `manual_override=false` та активним зовнішнім Move/Gather або cargo. Отже, відсутність прапорця не доводить ані нову професійну автоматизацію, ані завершення роботи. Рекомендація: нейтральний compatibility executor зберігає попереднє виконання без синтезу manual authority/нового наказу. Безпідставно доданий manual override змінить eligibility старої поведінки.

**Deferred не зберігає назву останньої команди.** `automation_enabled=false` може бути наслідком Stop або явного Assign з вимкненою автоматизацією. Відновлюється вже записана політика та момент її застосування; відтворити оригінальну назву команди або CommandReply неможливо. Після смерті або невдачі може лишатися pending leg для прибирання; це не підстава повторно допускати актора до роботи.

**Прапорці й terminal history не є журналом походження.** `retire_manual_override` не завжди одразу змінює `wait_reason`; підказка ManualOrder може тимчасово залишитися після завершення. Work і logistics мають обмежений хвіст історії. `complete_task` очищує `resume_job` після створення continuation; шукати її слід через активний Work/маршрут, не через останній Complete task. `PathBatchOutcome` не містить resident IDs або author/request; у WorldState немає server request cache. Оригінальне авторство, group ID і час видачі вже встановленого маршруту відновити не можна.

**Невдалий output не завжди завершує Gather.** Якщо `gather_yield` не знаходить сховище, він створює Ground output і Failed/StorageFull task, але лишає gather activity/route та видає XP за справжній output. Сам останній Failed task не робить ручний Gather terminal. І навпаки, Failed task із pending Logistics path — старий cleanup, не доставка з вантажем.

**Множина import-valid станів ширша за звичайні команди 0.9.** Професійний валідатор дозволяє `manual_override=true` за будь-якого активного Work або physical task, не обмежуючи це GatherContinuation/ToDropoff. Він може прийняти, наприклад, ручний BuildAssignment або pickup без gather resume metadata. Це не доказ, що така дія виникає через звичайні команди. Не виводити вигаданий Gather із ItemKind або Build із самого Job. Для таких станів потрібен погоджений compatibility binding або чітко обмежена політика підтримки; тихо видаляти їх не можна.

## Мінімальні рішення до заморожування DTO

1. **Compatibility binding.** Рекомендовано зберегти старий executor окремо від нової користувацької черги: `legacy continuation`, `cancel-at-boundary` та підтверджений `manual head` мають різні значення. Compatibility стан не повинен створювати другі task/path/резерви й новий control lease. Для import-valid нетипових ручних виконавців потрібна відповідь: opaque legacy binding чи явно документована відмова; перевага — збереження їхньої старої семантики.
2. **Atomic legacy batch.** Перетворення вже початого batch на нове часткове раннє виконання змінить tick прибуття й результати старого save. Рекомендовано залишати імпортованим v7 batches режим старого атомарного commit з його budget charges, а новим командам давати per-resident execution. Інакше потрібне явне рішення про допустиму зміну поведінки, а не заява про незмінене продовження.
3. **Невідоме походження.** Нові order IDs можна призначити детерміновано за resident ID; не називати їх оригінальними ID. Відсутні issuer/request/issued_tick позначити як невідомі/legacy, а не вигадувати їх із поточного tick. Зовнішні `path_results` лишити старими результатами без нового player receipt; `GameServer::load` починає новий epoch.
4. **Одне джерело ручного пріоритету.** Новий queue/compatibility стан керує manual override; збережене поле 0.9 не має стати другою незалежною істиною. Кореляції child executor → manual head перевіряються взаємно, але черга не володіє предметами вдруге.
5. **Перевірка перед перетворенням.** Спочатку повна стара семантична валідація v7, потім класифікація і додавання wrapper metadata, потім нова transactional валідація. Не «виправляти» старі route cells/frontier/deadlines під час import. Зміни полів, які зберігають семантику, й правила відхилення неоднозначних станів мають бути окремими рішеннями root.

## Що додати до capture та майбутнього gate

До наявного переліку [CONTROL_PLAN_UA.md](CONTROL_PLAN_UA.md) потрібні: v7, записаний після genuine v6 load без перепризначення; груповий pending Move/Gather із Deferred Stop лише одного учасника; `Complete/Started` Work разом із чинним ручним gather route; terminal cleanup path без cargo; ручний running Gather із попереднім Ground/StorageFull output, якщо такий стан досягається нормальним сценарієм.

Search/Reconstruct/Stage знімаються лише за фактично спостереженою фазою прийнятого batch ID. Малий маршрут може перейти через фазу всередині одного tick, тому підставлений enum не є genuine fixture. Наявний приклад нормального Move Search/Reconstruct — [persistence_tests.cpp](../tests/persistence_tests.cpp), `pending_path_search_roundtrip_and_resume`, seed1661/pop20 і далека walkable ціль; приклад великого shared batch — [path_planner_tests.cpp](../tests/path_planner_tests.cpp), seed6101/pop1500 → Mine(28,24). Точні нові capture ticks має підтвердити заморожений writer.

Для кожної категорії порівнювати legacy-семантику до/після міграції: старі paths/frontier/cursors, фізичні стеки, XP/remainder, професію й safe-boundary переходи. Новий checksum не зобов'язаний чисельно дорівнювати старому через додані поля; натомість два нові продовження одного мігрованого стану мають збігатися на кожному tick. Успішна міграція не доводить готовності всієї S07 або решти рушія.
