# Стан розробки Ribterra

Дата початку: 8 вересня 2026 року. Джерело вимог — наданий автором план редакції 1.4. Поточна завершена збірка **0.10.1: protocol 7/rules 7/generator 2/save 8** додає поіменне приймання Move/Gather, сталі ID й черги ручних наказів, одноразову доставку або збір до вичерпання, скасування та передачу керування між гравцями. Збереження черг продовжує професії, навички й фізичну логістику 0.9. Завершальне виправлення відновлює пропущені через затриманий ACK знімки на паузі та автоматично перепідключає клієнта з обмеженим безпечним повтором непідтверджених наказів. Контракти: [ручні накази](MANUAL_ORDERS.md), [навички](SKILLS.md), [сейви](SAVE_FORMAT.md); актуальні результати тестів, GPU, пакета й CI — [VALIDATION.md](VALIDATION.md). Усі 38 початкових вимог і V01–V03 залишаються чинними; P0, P1 та повний рушій не завершені.

Історична 0.8 додала GatherContinuation і BuildAssignment: збережуване очікування, bounded retry, вичерпання ресурсу й заміну будівельника; її версії — save 6, protocol 5/rules 5/generator 2. [WORK_INTENTS.md](WORK_INTENTS.md) зберігає цей контракт. Її локальні 40/40 CTest, GPU, benchmark і package smoke та CI `f62cea0` (Windows 40/40, Linux 26/26, UBSan 8/8) пройдено; це докази попередньої версії. FIFO-планувальник, двофазні path replies, серверна, RmlUi та SDL_GPU/D3D12-основа збережені.

## Поточна реалізація

Графічний клієнт і dedicated server використовують один авторитетний `GameServer`. Навіть локальна гра надсилає рух, збір і будівництво через серверну чергу, а інтерфейс отримує лише відфільтрований `ViewSnapshot`. Камера та UI не мають прямого доступу на запис до SimCore.

Окремий `RibterraServer` приймає direct IP:port через GameNetworkingSockets 1.6.0. Реалізовано:

- 2–4 мережеві сесії в одній кооперативній нації;
- перевірку protocol/rules/content, імені, request ID, меж і частоти команд;
- challenge/password proof та випадковий reconnect-токен;
- ідемпотентне повторення команди, закриття сесії для зміненого повтору, фази `Queued` → `Applied`/`Rejected`, типізовані причини path failure, phase-specific batched ack і курсор наступного request після reconnect;
- окремі пріоритетні канали команд, чату й знімків;
- видимий повний знімок, дельту від підтвердженого baseline, ack і resync;
- chunk-повні та chunk-дельта знімки, поділ максимум на 128 частин і атомарне складання на клієнті з межею 16 MiB та тайм-аутом 10 секунд;
- серверний Unicode-чат, rate limit, коротку історію та mute на рівні API;
- dedicated autosave кожні 60 секунд, якщо задано `--world`.

Формат сейва 8 зберігає chunk-и, їхні revision, обидва шари, портали, EnTT-компоненти, FIFO path batches, прогрес пошуку/реконструкції/staging, фізичні стеки, склади, резерви, логістику, будівельні замовлення та work intents із retry/deadline/attempts і курсорами планувальника. Додано професію, пріоритети, ручний/відкладений стан, вісім шкал XP/practice/abilities та курсор вибору роботи. Формат 8 також зберігає ручні черги та зв’язки виконавців; genuine format 7 мігрує без втрати професій/XP, фізичних предметів і pending paths та залишає `.v7.bak`. Genuine format 6 мігрує зі збереженням старих XP і точного planner/work/logistics state та `.v6.bak`. Контейнер зберігає `RIBSV2`, 96-байтовий header і FlatBuffers/zstd payload. Перед заміною тимчасовий файл перевіряється; попередній валідний слот зберігається як `.bak`. Формат 5 із `.v5.bak` переносить незавершене продовження збору в Work intent без повторного пошуку чи доставки. Формати 4/3/2 і текстовий 1 та їхні backup suffixes підтримані; оплачені споруди й фізичні резерви зберігаються. Fixtures та byte-level контракт описані в [SAVE_FORMAT.md](SAVE_FORMAT.md). Однаковий seed створює різні world ID.

Ресурс має власника й одну фізичну позицію: земля, склад, руки або будмайданчик. Носій переносить до 10 одиниць одного виду; pickup/dropoff використовують внутрішні маршрути, а резерв не дозволяє двічі забрати той самий предмет. Будівельна робота починається після повної доставки. Скасування й невдала доставка зберігають матеріали фізично; повернення після початку роботи спершу перевіряє ліміти. Попередня 0.7 має перевірки резервування, pickup, перенесення, часткової доставки та роботи; повторна локальна перевірка цих сценаріїв для 0.8 пройдена, включно з усіма 17 GPU кадрами логістики. Панель **Запаси** показує доступне, резерв, загальну кількість, вантажі, доставку, прогрес, працівників та скасування споруди; каталоги охоплюють п'ять мов.

Успішна доставка лишається Complete незалежно від повернення до збору. Окремий work intent має Waiting/PathPending/Complete/Failed та відокремлені failure і completion. Started означає передачу маршруту, Exhausted — нормальне вичерпання очікуваного ресурсу. Планувальник обмежує відвідування до 128 і admission до 32 за tick, максимум 64 спроби за 1200 ticks. Оплачений Work-майданчик без працівника чекає вільного мешканця тієї самої нації; прогрес продовжується після прибуття без нового списання. Прийнятий ручний наказ заміщує автоматичний намір, а відхилена постановка його зберігає. Внутрішні Work/Logistics paths не створюють зовнішніх CommandReply. Owner-only full/delta/removal передають стан роботи та workforce без дублювання inventory; локальне [приймання й CI 0.8](WORK_INTENTS.md) виконано.

Нативний Windows build використовує pinned vcpkg baseline і статичний release-triplet. Окремий `Renderer2D` приймає backend-neutral `Frame2D`: Presentation лише формує впорядковані geometry/text-команди Terrain → WorldOrdered → Fog → UI, а renderer володіє SDL_GPU/SDL_ttf ресурсами, letterbox input mapping та offscreen capture. Windows startup запитує D3D12; software backend вмикається лише явно для тестів. HLSL компілюється host-tool `shadercross` у DXIL і reflection під час збірки. Для headless додано optional `RIBTERRA_ENABLE_UBSAN`, preset `headless-ubsan` і цільові CI suites; їхній актуальний результат наведено у VALIDATION. Історично в рубежі 0.5 Linux CI пройшов усі чотири тодішні suites без runtime errors або compiler warnings.

RmlUi формує меню до створення світу та HUD поверх `Frame2D` без окремого render pass. Доступні New settlement, Continue, Settings, Help, Quit, ресурси/день/населення, вибраний мешканець, його шар і path phase/failure, будівництво, пауза/швидкість, save/load і серверний чат. `Queued`, `Applied`, `Rejected` та всі типізовані path failures мають повідомлення в English, українській, русский, polski й español. Surface/Mine та Page Up/Page Down перемикають лише шар перегляду. Use passage надсилає серверну команду переходу для вибраного мешканця біля відомого порталу. Фокус текстового поля блокує ігрові скорочення; чат та імена екрануються. F1 і Help Back зберігають чинну локальну або remote-сесію.

AssetPipeline допускає лише зареєстровані відносні шляхи в asset root і перевіряє SHA-256 та metadata manifest. Під час staging localization/font check та нативний `UiCheck` відхиляють некоректні каталоги, відсутні гліфи, RML/RCSS-помилки й unsupported render features до заміни попереднього комплекту. Окремий `AtlasTool` експортує PNG-сторінки з UV/pivot, provenance, notices і hashes. Деталі — у [ASSETS.md](ASSETS.md). Світ ще не малюється через production atlas.

Історично після виправлення `d9e35cc` локальний Windows-прогін 0.5 пройшов 30/30 тестів за 32.60 с без попереджень MSVC. `SimRunner` із seed 70421 після 160 ticks зберіг checksum `9495560223965183407`. Великий мережевий сценарій передав усі 128 chunk-ів у 19 частинах та охопив full join, late join, перехід у шахту, заборону керування чужою нацією, reconnect, timeout/resync, передчасний ack і продовження сейва. Повторні GPU, MineVisualProbe та розпакований server + два probes + GPU client пройдено; 23 PNG були переглянуті. Ці історичні результати не підтверджують поточний код 0.7.

Історичний Windows-прогін 0.4 пройшов 26/26 тестів за 26.58 с без попереджень MSVC, а фізичні D3D12 renderer і network GPU-сценарії пройшли на NVIDIA GeForce RTX 3050 Laptop. Windows CI 0.4 успішний. [CI 0.5 для commit `036b08b`](https://github.com/fipsyatina/ribterra/actions/runs/34213349737) має Windows success: 30/30 тестів за 26.88 с; Linux пройшов 10 із 19. Дев'ять тестів завершилися `std::bad_alloc` через переповнення signed `int` у генераторі рельєфу, тоді як `asset_tool` пройшов. Commit `d9e35cc` перетворює операнди в `uint32_t` до множення, додає три boundary-terrain regression tests і виправляє GCC structured-binding warning. У [новому CI](https://github.com/fipsyatina/ribterra/actions/runs/34214848608) Linux пройшов 19/19 за 15.06 с і UBSan 4/4 за 1.68 с без runtime errors або compiler warnings; Windows також успішний: 30/30 за 27.86 с.

## Межі поточної гри

Світ 0.7 має 128 наперед створених chunk-ів 32×32: по 256×256 клітинок поверхні та шахти в межах координат `[-96, 160)`. Це фіксована сітка без streaming/unload. Явний портал з'єднує `(28, 24, Surface)` і `(28, 24, Mine)`. `MineOre` блокує рух; мешканець збирає її із сусідньої клітинки, а виснажений тайл стає `MineFloor`. Перше відкриття входу додає лише відому клітинку парного виходу, не радіус шахти.

EnTT 3.16 є фактичним сховищем identity, position, activity, vitals, skills, routes і стану наказу. Один FIFO batch використовує спільний reverse BFS від цілі або її прохідних сусідів, канонічний порядок resident ID та не більш як 4096 одиниць пошуку, реконструкції й staging за tick. Успішні маршрути batch-а застосовуються разом; timeout, повторні зміни topology та ліміти дають типізовану terminal-відмову без часткового застосування. Зовнішні DTO сортуються за стабільним ID.

Звичайна сесія досі має одну керовану кооперативну націю, табір, будинок, ферму, склад, фізичні ресурси трьох видів, рух, збір, спрощені їжу/голод/сезон і три цілі навчання. Глобальний `Resources` тепер є похідною проєкцією фізичних запасів. Дороги, небезпека маршрутів, виробничі рецепти, апгрейди, каравани, псування їжі, повний каталог матеріалів і складна власність ще відсутні. Межа 6000 мешканців у валідації є тимчасовим захистом для чотирьох націй, а не підтвердженням продуктового масштабу. Ієрархія регіонів, flow fields, reusable route cache, crowd avoidance, колізії та повний AI не реалізовані.

Поточний reconnect працює лише в пам'яті запущеного сервера. Після перезапуску світ завантажується, але сесійні токени, ролі й кеш невизначених команд не відновлюються. Чат уже має графічну панель, але lobby/roles UI та persistent moderation відсутні. LAN працює як ручне підключення до адреси хоста; автоматичного discovery немає. Фізична сесія між двома ПК та Steam-сеанс ще не перевірені.

## Що ще потрібно для повного рушія

Чинними залишаються всі вимоги [ENGINE_REQUIREMENTS.md](ENGINE_REQUIREMENTS.md). Серед великих невиконаних блоків:

- D3D12 render performance gate, повне world atlas rendering, batching/culling/static-cache/hot reload, miniaudio та розширення AssetPipeline;
- streaming/unload chunk-ів, повна генерація біомів/геології/печер, path hierarchy/flow fields/cache/crowd avoidance/collisions та решта фізичної логістики/виробництва;
- родини, повні виконавчі сценарії професій/навичок, повний AI, здоров'я, суспільство, події, тварини та бій;
- карти з remembered/visible станами, маркерами, фільтрами й картографією;
- повне навчання, key rebinding, accessibility, lobby та решта ігрових екранів;
- durable session після restart, autosave ring, Cloud-конфлікти, LAN discovery і Steam adapter;
- реальні 4×1500, p95/p99 tick/render, RAM/VRAM, loss/latency/soak/sanitizer gates;
- фінальний контент, баланс, macOS і Steamworks/SteamCMD перевірки.

EnTT тепер підключено до `SimCore` і використано для поточних компонентів. Catch2 зафіксовано в manifest, але поточні тести його не використовують. Наявна ECS-основа не означає завершених AI, логістики чи performance gates. RmlUi/ICU milestone не означає готового frontend: немає lobby, повного набору colony screens, key rebinding, runtime UI hot reload, audio settings або texture registry для світу. SDL_Renderer використовується лише явним software test backend.

## Наступний інженерний рубіж

Ручні накази 0.10 продовжують [професії й досвід 0.9](PROFESSIONS_PLAN_UA.md). Move/Gather тепер приймаються окремо для мешканців групи; Shift додає наказ до черги. Панель показує активну чергу й останні завершення, дає скасувати один наказ або відпустити чи передати керування. Завершення доставки захищає фізичний вантаж; скасування внутрішнього повернення до збору не поновлює стару роботу. Відключений гравець має 30 секунд монотонного часу на повернення, включно з паузою. Деталі й межі — [MANUAL_ORDERS.md](MANUAL_ORDERS.md); ці механіки не закривають повний Utility AI, каталог професій або решту вимог рушія.

Найближчий етап — [виробництво на фермі 0.11](FARM_PRODUCTION_PLAN_UA.md): працівник, скінченна черга, збережувана праця й фізична доставка. Це план, реалізація ще не почата.

Наступний simulation-рубіж розширює вже реалізовані фізичні склади, резерви, перенесення й будівельні доставки виробничими рецептами та чергами, апгрейдами, дорогами, ризиком маршруту й рештою каталогу ресурсів. Наступні path-рівні мають додати hierarchy/flow fields/cache, crowd avoidance і колізії поверх поточної FIFO/shared-reverse-BFS основи. Навіть із детермінованими лімітами потрібні виміри 10/100/500/1500/4×1500 зі складним AI, чотирма клієнтами, save/load і memory/network/render показниками; поточний код сам по собі не закриває performance gate.

Durable reconnect після restart, autosave ring, LAN discovery, lobby/roles, audio та network loss/latency лишаються окремими обов'язковими блоками; фінальні performance gates мають вимірювати розширену симуляцію.

Після цього simulation/content блоки слід додавати вертикальними сценаріями, кожен із save/load, multiplayer, hidden-information і performance доказами. Терміни вихідного плану залишаються оцінками, а не підтвердженим графіком.
