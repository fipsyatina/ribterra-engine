# Ribterra save format

The Ribterra 0.10 writer emits format 8 saves, rules 7 and generator 2, in the existing `RIBSV2\r\n` container. The container header is 96 bytes and records the header version, zstd flag, save/rules/generator versions, compressed and decompressed lengths, a legacy FNV-1a-style container checksum (initial state 1469598103934665603, multiplication constant 1099511628211; the initial state differs from standard FNV-1a), the 16-byte world ID, and the 32-byte content hash. Payloads are zstd-compressed FlatBuffers with the `RBTW` file identifier. Compressed and decompressed payloads each have a 96 MiB limit. Implementation and test coverage described here do not establish release readiness; execution evidence is tracked separately in [VALIDATION.md](VALIDATION.md).

Format 8 appends manual orders and their next-ID and scheduler cursor. Each order records its resident and nation, request kind, optional layered target, Gather completion mode, phase, failure/completion reason, optional issuer, optional issued/activated ticks, compatibility flag, executor kind/ID, retry tick and attempts. Nullable ticks distinguish unknown provenance from a command genuinely issued at tick zero. Issuer IDs are historical metadata, not authorization; session control leases are not stored in the world. Known Move/Gather requests require a target; an opaque legacy executor may have none. The current payload requires the manual-order vector even when empty, positive counters, bounded enums and semantically valid reciprocal references. The total collection is bounded to 8192 records, with at most eight live orders per resident and 256 terminal records.

Manual completion values are `None=0`, `Arrived=1`, `Delivered=2`, `Exhausted=3`, `Replaced=4`, `Stopped=5`, `Released=6`, `LegacyFinished=7` and appended `Cancelled=8`. Cancelling one order records `Cancelled`; releasing resident control records `Released`. Both use the terminal `Cancelled` phase, but a single-order cancellation does not release the session control lease. The parser rejects values above 8, and semantic import rejects mismatched phase/reason pairs such as `Complete` with `Cancelled`. Focused persistence tests roundtrip both reasons, preserve the untouched queue head when cancelling a tail, and reject an invalid phase or enum transactionally.

Queue-head ownership is also validated: a `Queued` head cannot conceal an existing pending path, active work intent, physical task or non-idle job; queued tails may wait behind the head's executor. `PathPending` owns a path, while `Active` owns a route, Work intent or logistics task. A new `WaitingBoundary` order may bind the preceding physical task or accepted legacy path even when its requested next activity differs. Live legacy compatibility wrappers are limited to `Active` or `PathPending`; they cannot become newly scheduled opaque requests. The scheduler independently rejects an absent target before dereferencing it.

Path drafts append manual-order correlation, per-resident resolution and failure. Path batches append `legacy_atomic`, default true. New Manual batches can resolve participants individually; imported v7 batches retain their old atomic completion and budget. The frozen logical costs for an atomic legacy batch/draft/outcome are 256/72/48 bytes, preserving old acceptance boundaries despite the larger new C++ DTO. Existing points, frontier, work counters, timing and undrained outcomes remain authoritative.

Format 7 compatibility is frozen to rules 6, generator 2 and content hash `92e20f6f81770d8ca01a478753e8022ee600ca4fa9ddf0a88e07560043a23bcd`. The core migration helper first runs the old semantic validation, before adding queue wrappers. Confirmed manual heads receive deterministic new IDs in resident-ID order and bind the existing path, route, Work intent or logistics task; they acquire neither a new executor nor invented issuer/issue/activation time. Continuous legacy Gather stays UntilExhausted. Neutral v6-origin execution and already Deferred Assign/Stop retain their saved policy and physical boundary without new manual heads. Valid atypical manual executors receive opaque compatibility requests instead of fabricated Move/Gather provenance. Terminal history alone does not create an active order. Successful primary-file migration keeps the exact old container as `<save>.v7.bak` before replacing the primary. All newly appended fields, including explicitly present scalar defaults and the Manual path-command value, are rejected in older payloads.

Format 7 introduced exactly five additional XP values, eight practice records and eight ability contributions per resident, alongside the existing three XP fields. It requires profession assignment, optional layered worksite, five bounded job priorities, automation/manual/deferred state, wait reason and next evaluation tick. The stable resident scheduler cursor is also authoritative. Practice credit, familiarity debt and last useful-work tick are persisted; querying a modifier never modifies these fields. Missing or malformed current-format arrays, invalid enum values, inconsistent deferred/manual states and out-of-range persisted skill/ability inputs are rejected before commit. The skill balance data is included in the gameplay content hash. See [SKILLS.md](SKILLS.md) for the work and modifier contract.

Twenty-five [genuine format 7 fixtures](../tests/fixtures/WORLD_SAVE_V7.md) were captured with unchanged 0.9 headers/libraries from `d3bc785`, before any format 8 work. They cover external Move/Gather Search/Reconstruct/Stage, physical manual movement and gathering, cargo, Work Waiting/PathPending/Started/Failed, deferred policies, neutral v6-origin cargo, automatic mining, the profession cursor, earned XP/practice and an already paid construction worker. All re-encode byte-identically and match at each of 64 subsequent ticks in that original writer/loader, retaining undrained path outcomes. The frozen schema is `schemas/baseline/world_save_v7.fbs`; [provenance](../tests/fixtures/world_save_v7.provenance.json) records origin commands, hashes, complete checksum sequences and expected decoded state except chunks/empty tiles. The focused manual-order persistence suite compares every old field on migration and computes the frozen v7 checksum projection at all 65 historical checkpoints, alongside deterministic new-format save/load continuation. Fixture verification proves the historical inputs; the new migration test execution result is recorded separately in VALIDATION.md.

These fixtures exercise specific finite histories, not every valid v7 state or every future tick. Their innate ability contributions are all zero; they do not cover nonzero abilities, every profession or every manual executor combination. The separate opaque-executor test modifies only a temporary copy of the genuine neutral construction-cargo input to create an old-valid manual profile, then verifies lossless migration and continued save/load. That derived test is not another genuinely captured historical fixture. Malformed payload tests separately cover new-field version forgery, invalid references, queue/history bounds and transactional rejection; none rewrite the immutable historical inputs.

Format 6 compatibility is frozen to rules 5, generator 2 and content hash `3a8700a4682e31d8c14606093966cc57a322afded4c82480dddf306d2a85fbbe`. Migration preserves the old three XP values and all existing work/logistics/planner state; it does not rerun those older migrations. Added XP, abilities, practice credit and debt are zero; last-practice ticks start at the saved world tick, avoiding invented prior absence. Profession is Unassigned with automatic legacy assistance, no worksite or manual/deferred override, next evaluation zero and scheduler cursor one. Successful primary-file migration retains exact original bytes as `<save>.v6.bak` before replacing the primary with format 8. Recovery from a missing primary through its `.bak` loads without rewriting that backup. New-format fields inside legacy payloads are rejected even when a newly added scalar was explicitly written with its default value.

Format 8 retains the 256×256 surface and mine grids as exactly 128 chunks. Each chunk preserves its key, revision, and 1024 tiles. Residents and buildings preserve their layer and nation. Routes are keyed by resident ID and use layered cells; their optional work cell distinguishes no work from the valid coordinate `(-1, -1)`. Portals preserve their surface and mine endpoints. The required dense `tiles` vector inherited from format 2 is written empty, and a payload containing both dense tiles and chunks is rejected.

Pending path planning is saved as complete resumable state. This includes queue order, phase, resident reservations, command and build reservation data, deadlines and topology revision, roots, frontier and cursor, discovered parent nodes, exact floating-point route starts, reconstruction cursors, staged route cells, reservation flags, work counters, resident order status, and undrained terminal outcomes. Loading does not replay commands, repeat a storage-reservation work unit, or restart an unchanged search. Parser collection limits and the aggregate 64 MiB logical planner-state estimate are checked before constructing planner vectors; the estimate uses stable element costs rather than implementation-dependent allocator capacity and is not a bound on peak process memory. `World::import_state` then checks graph, phase, reservation, and resource invariants transactionally.

Serialization is deterministic. Chunks are ordered by layer, row, and column; residents, buildings, and routes are ordered by stable ID. Loading still performs the complete `World::import_state` semantic validation before changing the active world.

Physical inventory remains authoritative in format 8. Each item stack has a stable ID, item kind, quantity, owner nation, and exactly one ground, storage, carried, or construction location. Storages, item reservations, logistics tasks, construction orders, and their monotonic ID counters are serialized. A carried stack is the sole authority for its cargo; there is no second carry quantity to reconcile. Task phase, resident, reservation, source/carry stack, destination building, path correlation, deadline, failure, and suspended gathering activity all survive save/load. Construction orders preserve required and delivered quantities, phase, site, nation, and originating client path batch. The legacy resources table remains a checked derived projection.

The parser bounds collections before allocating inventory vectors: at most 65,536 stacks, 8,192 reservations, 4,096 tasks, no more storages than buildings, and at most 65,536 existing sites plus 512 pending path batches. Semantic import verifies the cross-references, quantities, phases, and ownership before commit. Runtime validation evidence is recorded in [VALIDATION.md](VALIDATION.md); these format rules alone do not establish release readiness.

Format 8 retains at most 8,192 work intents for gathering continuations and building workforce assignments. Each intent preserves its stable ID, kind, phase, completion/failure reason, resident/building/owner, target and expected terrain, job, creation and retry ticks, admission deadline, attempt count, correlated path batch, and topology revision of the last attempt. The next intent ID and scheduler intent/building cursors are saved as authoritative state. A waiting intent resumes its bounded admission schedule after load; an admitted one keeps the existing planner frontier, reconstruction and staging state. Neither a retry nor load recreates already-delivered cargo. Failed building assignments may be reconsidered after a topology change under the scheduler budget; completed or failed gathering continuations are not revived by migration.

Format 5 compatibility is frozen to format 5, rules 4, generator 2, and content hash `52e02f82fa53d54c22b9b3384f91d05a3ef01ef5373ce30c4e3698f52d7abf53`. Physical stacks, reservations, cargo, construction costs/progress and active hauling are retained. An old completed logistics task with a still-pending gathering path transfers that correlation into a PathPending work intent; the same batch ID and search state remain, with the internal command changed from Logistics to Work. The old task releases that path correlation. Unchanged planner state is not searched again, and older terminal failures do not become new work. A successful primary-file migration preserves the exact original as `<save>.v5.bak` and atomically writes format 8. Work-intent fields or the Work path-command value are rejected inside an older-version payload.

Three genuine format-5 fixtures were produced by normal gather/build commands using copied, unchanged 0.7 headers and SimCore/Foundation libraries, then loaded by the original 0.7 implementation: [active cargo at tick 57](../tests/fixtures/world_save_v5_carry.expected.json), [completed haul with pending gathering continuation at tick 115](../tests/fixtures/world_save_v5_continuation.expected.json), and [paid House work at tick 91](../tests/fixtures/world_save_v5_work.expected.json). The schema is frozen in `schemas/baseline/world_save_v5.fbs`; capture source, library/executable/schema/file hashes and expected state accompany the fixtures.

Format 4 compatibility is frozen to format 4, rules 3, generator 2, and content hash `de55d4ba8a19c142b2abf3a0f7492cc195ec601fc02171b6c370df382a8cb401`. Migration creates Camp stacks from the old global resources and physical reservations/tasks for each pending Build, retaining its building ID and path correlation. An unfinished building whose materials were already paid receives a Work order with delivered equal to required; its cost is not charged again. Completed buildings are retained. A valid legacy state that cannot be represented without loss is rejected before changing the active world. A successful primary-file migration preserves exact original bytes as `<save>.v4.bak` before atomically replacing the primary with format 8. New logistics fields or enum values inside a legacy-version payload are rejected.

The genuine [v4 fixture](../tests/fixtures/world_save_v4_builds.expected.json) was produced using unchanged 0.6 SimCore/Foundation libraries and checked by the original 0.6 loader. It includes a paid House at progress 0.01, a pending Farm with reserved cost 20 Wood/10 Stone/5 Food, and remaining global resources 50/25/100. Its schema is frozen in `schemas/baseline/world_save_v4.fbs`; source, hashes, and expected state accompany the fixture.

Format 3 compatibility is frozen to format 3, rules 2, generator 2, and content hash `939da049dcdef8353b0f8dc774e8334f135fbe9c49edb1a5a2becfe2e3617c0c`. Format 3 has no pending planner state, so migration initializes an empty queue and result drain, next batch ID 1, and topology revision 0. A resident with a non-idle job or unfinished route is marked active; other residents are idle. The physical-inventory migration then runs. A successful primary-file migration preserves the exact original bytes as `<save>.v3.bak`.

Format 2 compatibility is frozen to format 2, rules 1, generator 1, and content hash `74022768476accf5160ac236bfb85a43337b96195a29c21c83d1d594e29fdeaa`. Its 48×48 surface tiles retain coordinates 0 through 47 and are overlaid on a newly generated world. Existing residents, buildings, resources, tutorial flags, events, and positional routes are retained; migrated entities use the surface layer and nation 1. The generated mine and surrounding terrain remain deterministic for the original seed, and the canonical surface-to-mine portal is retained. Physical inventory is initialized through the same migration. A successful primary-file migration preserves the original bytes as `<save>.v2.bak`.

Legacy text format 1 follows the same 48×48 and inventory migration rules and preserves the original as `<save>.legacy.bak`. A missing primary may be recovered from the normal `<save>.bak`; a corrupt primary is reported instead of silently rolling back. Formats 1 through 5 also pass the work-intent migration; formats 6 and 7 preserve their existing work state. Formats 1 through 6 receive neutral profession/practice fields; format 7 preserves its existing profession and skills. Every older format then passes the manual compatibility migration exactly once. Ribterra writes only format 8.

## Genuine format 6 migration inputs

Eight [genuine format 6 fixtures](../tests/fixtures/WORLD_SAVE_V6.md) and a frozen `schemas/baseline/world_save_v6.fbs` were captured with the verified 0.8 source commit `f62cea0`. They cover physical cargo, Waiting, queued/partially searched Work paths, travelling/working replacement builders, Exhausted and deadline failure. Every file re-encodes byte-identically and compares equal at each of 64 subsequent ticks in the original writer/loader. [Historical verification](evidence/work-v6-fixtures.json). The current persistence suite checks exact backup bytes, unchanged old fields, neutral added fields, and 128 ticks of resumed simulation for each fixture. Runtime verification status belongs in VALIDATION.md; fixture provenance alone does not establish release readiness.
